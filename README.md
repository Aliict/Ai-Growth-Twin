# AI Growth Twin

An AI employee that continuously discovers, predicts, and fixes SaaS revenue problems.

Creates a digital "growth twin" of a SaaS business and analyzes user behavior, funnels,
revenue, and product usage to increase free trial → paid conversion.

## Core features

1. **Executive Dashboard** — MRR, ARR, activation, paid conversion, revenue leakage,
   expansion opportunity, LTV, CAC, payback period, LTV:CAC ratio
2. **Funnel Analyzer** — signup → activation → project creation → team invite → trial
   usage → paid, with per-stage dropoff and revenue impact
3. **Revenue Leak Detector** — rule-based detection of onboarding friction and lost revenue
4. **AI Experiment Generator** — an LLM proposes a hypothesis and expected effect size; a
   separate statistical engine then *simulates a randomized trial* against it (two-proportion
   z-test, p-value, 95% confidence interval) so results are measured, not just described
5. **Revenue Simulator** — "what if activation increases by 10%?" MRR projections
6. **AI Founder Advisor** — retrieval-grounded chat: business data is chunked, ranked by
   TF-IDF relevance to the question, and only the top matches are given to the LLM as context
7. **AI Product Roadmap Generator** — quarterly roadmap ranked by revenue impact
8. **Growth Twin Engine** — a RandomForest conversion-probability model and a
   LogisticRegression churn-probability model, both trained on the company's own trial-user
   history, drive the MRR/churn/conversion forecast (replacing a fixed-percentage heuristic)
9. **Analytics** — signup cohorts, a retention curve, acquisition-channel and plan-tier
   breakdowns, and a linear-regression MRR forecast with a confidence band

## What's real vs. what's simulated

This is a portfolio-grade prototype, not a production SaaS with real customers — being
precise about what's actually computed vs. what's assumed data is the point.

| Area | What's real | What's simulated / assumed |
|---|---|---|
| Funnel, dashboard, revenue math | All arithmetic (rates, MRR/ARR, dropoff $, LTV, CAC, payback) is computed live from whatever `TrialUser` rows exist in the DB — nothing is hardcoded. | The 500 `TrialUser` rows themselves are synthetic, generated by `app/scripts/seed.py` with hand-picked probabilities (55% activation, etc). Plan prices and channel CAC/cost-per-signup (`app/core/pricing.py`) are made-up but fixed assumptions, not observed spend. |
| Growth Twin ML models | `RandomForestClassifier` (conversion) and `LogisticRegression` (churn) are genuinely trained via scikit-learn on the seeded `TrialUser` rows every time you refresh; AUC/accuracy/feature importance are real sklearn output, not fabricated. | Trained on ~500 synthetic rows, so the metrics reflect how well the model fits *this synthetic dataset's assumptions*, not a real product's user behavior. With too little data, the API returns `insufficient_data: true` and falls back to observed rates instead of a hallucinated forecast. |
| Experiment engine | Given a baseline conversion rate and a hypothesized effect size, `app/services/experiment_engine.py` runs an actual `numpy` binomial simulation and a real two-proportion z-test (p-value, 95% CI) — this is standard A/B-test statistics, not an LLM guessing. | There's no real traffic being split — the "control" and "variant" populations are simulated draws, not live users. The *effect size* it tests against comes from the LLM's hypothesis, which is a guess. |
| AI Advisor | Retrieval is real: `app/services/advisor_retrieval.py` builds ~15-20 text documents from live funnel/revenue/experiment/retention/Growth-Twin data and ranks them against the question with TF-IDF + cosine similarity (scikit-learn) before either prompting the LLM or, if no API key is set, directly returning the top-ranked document's text. | Not LangChain (not a project dependency) and not a vector DB — this is intentionally lightweight retrieval, not a large-scale RAG pipeline. |
| Experiment/roadmap generation | — | The hypothesis text, "suggested_variant" copy, and expected uplift/revenue numbers are LLM output (or a fixed fallback string when no `OPENAI_API_KEY` is set) — treat these as creative suggestions to be tested, not measured facts. |
| PostHog | `app/services/posthog_events.py` fires real `posthog.capture()` calls — `user_signed_up`, `user_activated`, `funnel_stage_changed`, `subscription_started`, `churned`, `experiment_created`, `experiment_completed` — including backfilling the seeded users' historical journeys with correct past timestamps. | Requires a real `POSTHOG_API_KEY` to actually send anything; with no key set, every call is a safe no-op (`posthog.disabled = True`) and the app works identically. This app does not read analytics back out of PostHog — its own dashboard is computed from the SQL database, independent of whether PostHog is configured. |

## Stack

- **Backend**: Python 3.12, FastAPI, PostgreSQL (SQLAlchemy + Alembic migrations), Redis, Celery
- **ML**: scikit-learn (RandomForestClassifier, LogisticRegression, LinearRegression, TF-IDF retrieval)
- **Frontend**: Next.js 15, React, TypeScript, TailwindCSS, shadcn/ui, Recharts
- **AI**: OpenAI GPT-4o-mini (optional — see fallback behavior above)
- **Analytics**: PostHog (optional — see fallback behavior above)
- **Testing**: pytest (21 tests covering revenue math, ML training, the experiment engine's
  statistics, funnel monotonicity, and cohort/retention calculations)
- **Infra**: Docker Compose

## Running locally with Docker

```bash
cp .env.example .env   # fill in OPENAI_API_KEY / POSTHOG_API_KEY if you have them
docker compose up --build
```

The `backend` container runs `alembic upgrade head` automatically before starting, so tables
exist as soon as it's up. Then seed demo data (a sample company with 500 trial users,
backfilling PostHog events too if `POSTHOG_API_KEY` is set):

```bash
docker compose exec backend python -m app.scripts.seed
```

- Frontend: http://localhost:3000
- Backend API docs: http://localhost:8000/docs

## Running without Docker

The `.env` file always lives at the **project root** (next to this README, one level above
`backend/`) — `app/core/config.py` resolves it by an absolute path, so it's found the same way
regardless of which directory you run `uvicorn`/`alembic`/`pytest` from.

```bash
cp .env.example .env   # then fill in DATABASE_URL and any API keys you have
```

If you're pointing `DATABASE_URL` at a managed Postgres (Neon, Supabase, RDS, etc.), make sure
the scheme is `postgresql+psycopg://...` — this project uses the `psycopg` v3 driver, not
`psycopg2`, so a plain `postgresql://` URL (what most providers give you by default) will fail
to connect until you add the `+psycopg`.

### Backend

```bash
cd backend
python3.12 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
# requires Postgres + Redis reachable at DATABASE_URL/REDIS_URL (local install, Docker, or a
# managed provider like Neon) — see the .env note above
alembic upgrade head    # creates the schema
python -m app.scripts.seed
```

Dev mode (auto-reloads on code changes):

```bash
uvicorn app.main:app --reload
```

Production-style (no reload, matches how the Docker image runs it):

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

- Backend: http://localhost:8000
- API docs: http://localhost:8000/docs

### Database migrations

Schema changes are managed with Alembic (`backend/alembic/`), driven by `app.core.config`'s
`DATABASE_URL` rather than a hardcoded URL in `alembic.ini`. Table names are derived
automatically from each model's class name (see `Base.__tablename__` in
`app/core/database.py`), not repeated per-model.

```bash
alembic upgrade head                              # apply all migrations
alembic revision --autogenerate -m "add X column"  # after changing a model
alembic downgrade -1                              # roll back one migration
```

Celery (optional, powers the periodic Growth Twin snapshot):

```bash
celery -A app.core.celery_app.celery_app worker --loglevel=info
celery -A app.core.celery_app.celery_app beat --loglevel=info
```

Tests (no Postgres/Redis required — they run against an in-memory SQLite DB):

```bash
pip install -r requirements-dev.txt
pytest
```

### Frontend

```bash
cd frontend
cp .env.local.example .env.local   # NEXT_PUBLIC_API_URL, defaults to http://localhost:8000
npm install
```

Dev mode (hot reload):

```bash
npm run dev
```

Production build (matches how the Docker image runs it — build once, then serve):

```bash
npm run build
npm run start
```

Either way: http://localhost:3000 (redirects to `/dashboard`). It needs the backend already
running at the URL in `.env.local` — start that first, or the dashboard will show a
"Couldn't reach the API" error instead of data.

## Known limitations

- **Single-tenant demo mode**: the API always operates on the first seeded `Company` row
  (`app/api/deps.py`). There's no authentication or multi-tenancy — swap
  `get_demo_company_id` for a real auth dependency before this could serve more than one
  company.
- **Small training set**: 500 synthetic trial users is enough to demonstrate a real training
  pipeline (and the code explicitly detects and reports when it isn't enough — see
  `insufficient_data` above), but the resulting model metrics shouldn't be read as if they
  came from a mature production dataset.
- **No live traffic splitting**: the experiment engine simulates a trial statistically; it
  doesn't integrate with a feature-flag system or route real users into control/variant
  buckets.
- **PostHog is not read from**: this app writes events to PostHog (if configured) but all of
  its own dashboards, funnels, and models are computed independently from the SQL database —
  PostHog here is an audit trail / integration demo, not a data source for this app.
- **No CI/CD or deployment**: this is intentionally a local-only prototype (per project scope).
